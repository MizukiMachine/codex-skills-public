# Q&A Step Workflow

小さなQ&Aを積み重ねて対話しながら要件定義・設計・意思決定・理解を進める。

**重要: 質問には必ず番号付きの選択肢を添える。1往復の待ち時間を減らすため、互いに依存しない質問は1ターンに最大4問（Q1〜Q4）までまとめて提示してよい。ユーザーは `Q1:2 Q2:1` のようにまとめて回答できる。説明が必要な質問は、説明文を質問文の冒頭に内蔵する。質問の前のテキストは直前の回答へのフィードバック専用とし、長文を読ませない。Understandingモードの理解確認では、正解番号を固定しない。**

このスキルには2つのモードがある。ユーザーの入力に応じて適切なモードを選択する。

## モード判定

Phase 1（意思確認）の回答内容で判定する：

- **Decision モード**: 決定すべき事項がある（設計、技術選定、仕様決定等）
- **Understanding モード**: 対象を理解したい（概念の理解、コードの解説、仕組みの学習等）

両方が混在する場合は Decision モードを優先し、理解が必要な箇所で Understanding モードに切り替える。

## 全体フロー

```
[入力] → [Phase 0: コンテキスト収集] → [Phase 1: 意思確認]
       → [Phase 2: 決定グラフ生成] → [Phase 3: 対話ループ] → [Phase 4: 最終出力]
                                                         ↑        │
                                                         └── back ┘
```

## Phase 0: コンテキスト収集（非対話）

ユーザーに質問する前に、以下を自動収集する：

- プロジェクト/対象の現状構造
- 既に決まっていること（技術スタック、規約、制約）
- 関連する既存データ（SPEC.md、AGENTS.md、既存コード等）

収集結果は内部保持し、Phase 2の材料にする。

## Phase 1: 意思確認（1問）

ユーザーの目的を確認する質問を1つ投げる。
選択肢には目的の方向性を2〜4個提示し、ユーザーが最も近いものを選ぶ。

この回答がモード判定と以降の全質問の起点になる。

## Phase 2: 決定グラフ生成（非対話）

Phase 0のコンテキスト + Phase 1の回答から、決定すべき変数リストを生成する。

### 変数の構造

| フィールド | 内容 |
|---|---|
| id | 一意識別子 |
| question | ユーザーに提示する質問文 |
| candidates | 選択肢（2〜4個）+ 各々の説明 + recommendedフラグ |
| depends_on | 依存する他の変数のIDリスト |
| classification | Ask（ユーザーに聞く）または Auto（自動決定） |
| auto_reason | Autoの場合、自動決定の理由 |

### Ask と Auto の分類ルール

**Askにする条件（いずれか）：**
- 複数の正当な選択肢があり、ユーザーの意図に依存する
- 方向性に大きな影響を与える決定
- ユーザーが明確な好みを持つ可能性が高い
- 後からの変更コストが高い

**Autoにする条件（全て）：**
- 既に決まっている（慣例・規約がある）
- 技術的に自明な選択肢が一つに絞られる
- ユーザーが変更する可能性が低い

### 候補生成ルール（推奨順、2〜4個）

1. 既存の慣例/使用実績があるもの（一貫性維持）
2. 既に導入済みのもの（追加コストゼロ）
3. エコシステムの主流な選択肢
4. 異なるパラダイムの代替を1つ
5. 文脈に合わせた具体性（汎用すぎる選択肢は避ける）

### 依存ツリー（DAG）

```
[根（大決定）] ← depends_on: [] → 最初に聞かれる
  ├─ [中決定A] ← depends_on: [根]
  │    └─ [葉決定X] ← depends_on: [中決定A]
  └─ [中決定B] ← depends_on: [根]
```

上流の回答が変わると下流の候補も変わりうる。だから1問ずつ順番に聞く。

## Phase 3: 対話ループ（1往復ずつ）

依存ツリーの根から順に進める。

### 各ターンの構成

1. 質問文を提示する（Q1〜の番号を付ける）
2. 各質問に候補を推奨順に番号付きで2〜4個提示する。推奨候補は**先頭**に置き、末尾に `（推奨）` を付ける。各候補には1行の説明を添える
3. 「番号で回答。自由記述も可」と末尾に明記する

### 質問のまとめ提示（往復削減）

- 未回答のAsk変数のうち、depends_on が満たされ**かつ互いに依存しない**ものは、1ターンに最大4問（Q1〜Q4）までまとめて提示してよい
- 回答が他の質問の候補に影響しうる変数は、必ず単独で聞く
- 迷ったら単独で聞く（誤った前提の候補を見せるより往復が増える方がまし）

提示例：

```
Q1: 状態管理はどうしますか？
  1. Zustand（推奨）— 既にプロジェクトで使用中。一貫性を保てる
  2. React Context — 追加依存なし。小規模なら十分
  3. Redux Toolkit — エコシステムが大きいが導入コスト高

Q2: テストランナーはどうしますか？
  1. Vitest（推奨）— Vite採用済みなので相性が良い
  2. Jest — 実績豊富だが設定が重い

「Q1:1 Q2:2」のように番号で回答してください（自由記述も可）。
```

### ユーザーの入力パターン

| 入力 | 動作 |
|---|---|
| 番号 | 該当候補を選択 |
| 自由記述 | その内容を回答として扱う |
| `auto` / `任せる` | recommended候補を自動選択 |
| `back` / `戻る` | 直前の質問に戻る。下流の回答も連鎖的に無効化 |
| `summary` / `一覧` | 現在の決定状況（決定済み・残り・自動決定予定）を表示 |

### 回答と事実の矛盾チェック

ユーザーの回答が Phase 0 で収集した事実（コード・設定・ドキュメント）と矛盾する場合、黙ってユーザーの回答を採用しない：

1. 根拠（ファイル名・該当箇所）を添えて矛盾を指摘し、どちらが正しいか確認する
   （例: 「PostgreSQLとのことですが、`config/database.yml` には sqlite3 とあります。どちらが正しいですか？」）
2. 確認の結果を正として、下流の質問・候補を生成する
3. ユーザーの記憶違いと判明した場合、その回答に依存していた既回答があれば連鎖的に見直す

### 次の質問の選び方

未回答のAsk変数のうち、全ての depends_on が満たされている最初のものを提示する。

### 途中サマリー

5問に1回、または重大な決定の直後に、現在の状態を一覧表示する。

### 終了条件

| 条件 | 動作 |
|---|---|
| 全Ask変数が回答済み | 自動的にPhase 4へ |
| ユーザーが「完了」 | 未回答が残っていれば一覧表示し、「未回答を置いて進むか？」確認 |
| 残りが全てAuto | ループを自動完了しPhase 4へ |

## Phase 4: 最終出力

### Decision モードの場合

全決定（ユーザー回答 + 自動決定）をまとめて成果物を生成する。

1. 全決定を一覧化したドキュメント
2. ユーザーによる最終確認
3. 保存先の選択（ファイル保存等）

### Understanding モードの場合

理解の到達点をまとめる。

1. 対話を通じて確認できた理解ポイントを一覧化
2. ユーザーが「まだ分からない」と言った箇所は未解決として明記
3. 次にどこから掘り下げるべきかの提案

---

## Understanding モードの詳細

Decision モードのPhase 2-3と同じ1問ずつの原則を踏襲しつつ、以下の違いがある。

### Phase 2 の違い（Understanding モード）

決定グラフの代わりに「理解すべき概念の依存リスト」を生成し、各概念を**マイクロステップ**（2〜4文で言える知識単位）に分解する。

各概念は以下の構造を持つ：

| フィールド | 内容 |
|---|---|
| id | 一意識別子 |
| concept | 理解すべき概念名 |
| micro_steps | 2〜4文の説明単位のリスト（1概念につき2〜5個） |
| depends_on | 前提となる概念のIDリスト |

生成ルール：
- 前提知識から順に並ぶ（依存の根から葉へ）
- 各概念は前の概念を理解していなければ理解できない構造にする
- 1セッションで扱う概念は3〜10個程度に絞る
- 各マイクロステップは「その説明だけ読めば次の質問に答えられる」自己完結性を持たせる

### Phase 3 の違い（Understanding モード）

**原則: 長い説明をしてから「理解できたか」確認するのではなく、「2〜4文の新情報＋その内容を問う質問」をマイクロステップとして積み重ねる。読む負担を最小にし、理解度は内容質問の正誤で測る。往復の待ち時間を減らすため、1ターンに2〜4ステップをまとめて提示する（チャンク）。**

#### 1往復（チャンク）の構成

1. 冒頭テキスト: 前チャンクの答え合わせのみ（初回チャンクでは不要）。書き方は後述
2. Q1〜の番号付きで2〜4問を提示する。**各質問の冒頭にそのステップの新情報（2〜4文）を書き、続けてその説明を適用すれば答えられる内容質問と選択肢2〜4個を書く**

#### 答え合わせの書き方（チャンク冒頭、各問1〜3文）

- **正答**: 正解番号を明示し、正解の内容を改めて言い直した上で、**一歩踏み込んだ補足を1文**添える（例外、実務での意味、よくある誤解など）
  ```
  Q1: ✅ 2番が正解。キャッシュに無ければリゾルバはまずルートDNSに聞く。
      ちなみにルートの応答もキャッシュされるので、実際は毎回ルートに行くわけではない。
  ```
- **誤答**: 正解番号と正しい内容を示し、選んだ選択肢がなぜ違うか（どこで誤解しやすいか）を1文で
- 「正解！」だけで終わらせない — 事実の言い直しが理解の確定と定着になる
- 各問3文を超えない — 補足が膨らむなら次のマイクロステップに回す

```
Q1: DNSは名前→IPの電話帳。ブラウザはまずOSのリゾルバに聞く。
    では、キャッシュに無い名前のとき、リゾルバは次にどこへ？
  1. example.com本体
  2. ルートDNSサーバー
  3. ブラウザに聞き返す

Q2: ルートDNSは「.com担当はあちら」と紹介だけする。
    では、最終的なIPを答えるのは誰？
  1. 権威DNSサーバー
  2. ルートDNSサーバー
  3. ブラウザ

「Q1:2 Q2:1」のように番号で回答してください。
```

質問設計のルール：
- **新情報を省略して質問だけを裸で出さない** — 説明は必ず質問文に内蔵する
- 同一チャンク内の各ステップは、前の問いの**回答**に依存しないこと（新情報を順に読めば答えられる構成は可）
- 「理解できましたか？」型のメタ質問は使わない
- 誤答選択肢は、ありがちな誤解を反映したもっともらしいものにする
- Understandingモードの理解確認では、Decisionモードの「推奨候補を先頭」ルールを適用しない。選択肢に `（推奨）` を付けず、正解は内部で管理する
- Understandingモードでは、正解番号を 1 に固定しない。同一チャンク内で正解番号を 1/2/3/4 に分散し、同じ正解番号が続く場合でも2問連続までに抑える
- 選択肢はまず正答と誤答を作り、その後に順序を入れ替える。2択なら正解位置を 1 と 2 で交互にし、3〜4択なら直前チャンクも見て偏りを避ける

#### チャンクサイズの適応

| 状況 | 次チャンク |
|---|---|
| 全問正答 | 3〜4問を維持（テンポ優先） |
| 誤答が1つ以上 | 誤解したステップを1問ずつに縮小し、より小さい単位に分解して別の角度から再提示 |
| 同じステップで2回誤答 | 前提となる概念（depends_on）に立ち返る |

ユーザーの入力パターン：

| 入力 | 動作 |
|---|---|
| 番号 | 次チャンク冒頭で各問1〜3文の答え合わせをし、次のチャンクへ |
| `分からない` | そのステップをさらに小さい単位に分解して再提示 |
| `back` / `戻る` | 前の概念に戻って復習 |
| `skip` / `飛ばす` | その概念を保留にして次へ |
| `summary` / `一覧` | 現在の理解状況（理解済み・途中・未到達）を表示 |

### ガイドライン

- 説明はIT文脈で行う（現実世界の例えは使わない）
- **冒頭テキストは前チャンクの答え合わせ専用**（各問1〜3文）。新情報は質問文に内蔵する。各ステップの新情報が4文を超えるならマイクロステップの分割が粗いサイン
- ユーザーが「分からない」と言ったら、決して同じ説明を繰り返さず、別の角度やより小さな単位に分解する
- 質問は常に内容を問うもの（適用・予測・区別）にし、「はい/いいえ」「理解できた？」は使わない
- 5概念に1回、それまでの理解の全体像を箇条書きの短いサマリーとして表示する

## ガードレール

**やらないこと：**
- 互いに依存する質問を同時に出さない — 回答が他の質問の候補を変えるものは単独で聞く
- 1ターンに5問以上出さない — まとめるなら最大4問（Q1〜Q4）
- 候補なしで自由入力だけにしない — 必ず候補を提示
- Understandingモードで、すべての正解を同じ番号にしない — 選択肢順序から答えを推測できてしまう
- 長文を読ませてから簡単な確認質問をしない — 説明は質問文に内蔵し、冒頭テキストはフィードバック専用
- 説明なしで質問だけを裸で出さない — Understandingモードでは各質問文の冒頭に新情報を必ず含める
- 推測を事実のように提示しない — 推測は候補の1つに留める
- 既存の文脈と矛盾する候補を出さない
- 変更が困難な決定を後回しにしない

**やること：**
- ユーザーの回答が収集済みの事実と矛盾したら、根拠を添えて指摘し確認してから進む
- 前の回答を考慮して次の候補を絞り込む
- 「なぜこの候補を出したか」の理由を短く添える
- backで前の質問に戻れるようにする
- 自動決定したものは「何を・なぜ」を必ず開示する
